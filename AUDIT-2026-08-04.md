# Personal Health — Full-Stack Audit (2026-08-04)

Audit of all three codebases: `personal-health-backend`, `personal-health-frontend`,
`personal-health-android`. Each was built/run, then audited for hardcoded values and
for things that are described as built but are not actually wired up.

Rules audited against are from `.claude/CLAUDE.md`: no hardcoded IPs, no "ActiveBharat"
branding, single accent colour `#06b6d4` on dark theme `#0a0e1a`/`#111827`.

## 2. Breaking — deliberately NOT fixed (these are product decisions, not audit fixes)

### 2.1 Android config split-brain — FIXED

**Status: fixed.** `app.config.js` is now the single source of truth; `app.json` is reduced
to a stub whose only content is a comment explaining that Expo ignores it.

Added to `app.config.js` **and** to the committed `AndroidManifest.xml` (both were needed —
the manifest is committed source, not prebuild output, which is why config alone would not
have fixed it):
`ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `RECEIVE_BOOT_COMPLETED`, `RECORD_AUDIO`.

Two further breaks surfaced while fixing this:
- **`scheme: "personalhealth"` existed only in the inert `app.json`**, so the deep-link
  scheme never reached the build at all — `InviteAcceptScreen.js` handles
  `personalhealth://invite/{token}` and could never have been triggered. Scheme added to
  `app.config.js`. *Still outstanding:* the committed manifest has no `intent-filter` for
  the scheme, so deep links need that added before they work on a built APK. Not done here
  because the invite endpoints behind it are themselves missing (§2A).
- **Dev backend host ignored `BACKEND_HOST`**, hardcoding `'localhost'` — which on a
  physical device means the phone itself. Now honours the env var.

Verified: `npx expo config` resolves name `Personal Health`, slug `personal-health`, scheme
`personalhealth`, and all seven permissions.

Deliberately left: `com.activebharat.app` package / bundle identifier. Changing an app's
identifier breaks signing, installs and store listings — that is a release decision, not a
branding cleanup.

Original finding follows.



`app.json` and `app.config.js` both exist. **Expo uses `app.config.js` exclusively and does
not merge `app.json`.** Confirmed via `npx expo config` resolving `name: 'ActiveBharat'`
(from `app.config.js`), not `app.json`'s `'Personal Health'`.

Consequences:
- `app.json`'s `android.permissions` — `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`,
  `RECEIVE_BOOT_COMPLETED` — **never reach the build.** Verified against the authoritative
  `android/app/src/main/AndroidManifest.xml`: no location permissions present.
- `src/screens/social/MapScreen.js` calls `expo-location` regardless.
- **This is a real runtime break on a physical device, not a config nit.**
- `app.json`'s hardcoded IP `172.17.69.181` (line 75) is therefore dead/unused.

Not fixed because *which config file survives* is an architectural call for the owner.

### 2.2 On-device inference is dead code — REMOVED

**Status: removed** in `22b3f88`, per owner decision to keep Expo Go. Deleted
`poseClassifier.js`, `VisionTrainCamera.js`, both copies of `pose_classifier.tflite` (JS
assets and the native `android/` assets dir), and the model's norm-params/metadata — 359
lines. Verified the Metro bundle still compiles (1347 modules). Inference stays server-side
via `expo-camera` → `POST /session/{id}/frame`. Original finding follows.



`src/services/poseClassifier.js` is a complete TFLite on-device implementation, with a
bundled `assets/pose_classifier.tflite`. But:
- it is **imported by nothing** in the app;
- its dependency `react-native-fast-tflite` is **not in `package.json`**.

It would throw on import today. Additionally, `react-native-fast-tflite` is a native module
that **Expo Go cannot load**, which directly contradicts VISION.md's "Runs in Expo Go — no
build required". One of those two promises has to give — that is a product decision.

### 2.3 Coach invite flow is non-functional at both ends — REMOVED

**Status: removed** in `309c9b3` (backend) and `ee04201` (frontend), per owner decision.

An earlier draft of this audit said the endpoint had no callers. **That was wrong** — there
were two live UI surfaces, and the modal's failure path *fabricated* a plausible-looking
link (`/invite/demo-token-<random>`) and presented it as copyable, while the copy claimed
"they'll join your roster automatically". Deleting only the backend would have made that
fabrication the normal path, so the UI was removed with it.

A **third**, opposite-direction invite flow remains and is still broken: Android's
`ShareCardScreen` → `coachInvite.js:8` posts to `/athlete/{id}/request-coach`, which does not
exist. It rethrows, so the share sheet silently never opens (no fabricated data). Left in
place — it is a separate decision from the coach→athlete flow that was removed.

Original finding follows.



`routes/coach.py::generate_invite_link` mints `uuid4().hex[:12]` and returns it. The token
is **never persisted** (confirmed: no `invite` references in `sqlite_store.py` or
`database.py`), and there is **no `/join` route** in the frontend or Android deep links.
So nothing can ever validate an invite link. Coach acquisition is GTM Step 4 in VISION.md.

*Note: the branding fix above made this URL correctly point at a route that cannot work.*

### 2.4 Billing is a stub

`routes/coach.py:256` — `# TODO: actual payment system needed — this is a placeholder`,
returns `{"ok": True}` unconditionally. Milestone 5 is "First revenue."

### 2.5 LLM coaching layer silently runs in fallback

`ANTHROPIC_API_KEY` is unset (only `.env.example` exists), so `ai_coach.py` always takes the
deterministic-template path and reports `source: "fallback"`. Layer 3 "Generative" — the part
VISION.md says people pay for — is not actually exercised. Config is already correct; this
just needs a key supplied by the owner.

## 2A. Client↔backend endpoint gap — why the apps feel "half-baked"

Systematic check: extracted every `api.<verb>('/path')` call in
`personal-health-frontend/src` and `personal-health-android/src`, normalised the path
params, and diffed against the live backend OpenAPI spec (108 routes).

**24 of 73 distinct client API calls (33%) hit routes that return 404.**

### Why it looks like "built but empty" rather than "broken"

`src/lib/api.js:149` — `safeQuery(fn, fallback)` catches **every** error and returns the
fallback. Android equivalents use bare `catch (_) {}`. So a 404 renders as zeroed or empty
data, not a visible failure. Features look shipped-but-unused instead of unbuilt. This is
the single biggest reason the state of the app is hard to read from the UI.

### Class 1 — wrong path, backend works (FIXED)

| Client call | Real route | Where |
|---|---|---|
| `/athlete/{id}/streaks` | `/streak/{id}` | `AthleteHomePageContent.jsx:69` |
| `/inbox/athlete/{id}` | `/coach/inbox/athlete/{id}` | `MessagingPage.jsx:57` |
| `/athlete/{target}/claps` | `/athlete/{clapper}/clap/{target}` | `FeedPage.jsx:192` |
| `/athlete/{id}/weak-joints` | `/weak-joints/{id}` | `MetricsScreen.js:151` |

The clap call also had **inverted parameters** — the `{athlete_id}` segment is the clapper
and is ownership-checked against the caller, so passing the target would have 403'd even
with the right path. Response shapes verified against the live API. Commits `cff7839`,
`6cee422`.

### Class 2 — no backend at all (NOT fixed — needs a build decision)

Whole features exist as UI with no server side. Grouped by feature:

| Feature | Missing routes | UI that exists |
|---|---|---|
| **Wellness** | `/athlete/{id}/wellness`, `/wellness/score`, `/wellness/trends`, `/wellness/checkin` | Android `WellnessScreen`, `WellnessLogFormScreen`; frontend home check-in |
| **Nutrition / meals** | `/athlete/{id}/meals`, `/meals/{}/{}`, `/nutrition/goals`, `/nutrition/summary` | Android `MealLogScreen`, `NutritionScreen`, `NutritionGoalsScreen`; frontend home |
| **Share card** | `/session/{id}/share-card` | Android `ShareCardScreen`, `FirstScoreScreen` |
| **Invite / join** | `/invite/{token}`, `/invite/{token}/accept`, `/athlete/{id}/request-coach` | Android `InviteJoinScreen`, coach-invite prompt on share screen |
| **Misc** | `/athlete/{id}/achievements`, `/athlete/{id}/intelligence-report`, `/leaderboards/improvers`, `/coach/{id}/priorities` | frontend athlete home, coach dashboard |

Notes:
- Backend has only `/nutrition/analyze` and `/nutrition/classifier/status` — no per-athlete
  nutrition persistence whatsoever, despite three Android screens for it.
- **Share card is nearly there but not a path fix.** The backend serves
  `/session/{id}/scorecard` (+ `.png`), whose docstring says "for the Android app to render
  natively" — but it returns raw metrics (`avg_form_score`, `bpi`, `rep_count`) while the
  Android screen renders a presentation DTO (`hero_number`, `hero_label`, `chip_colour`,
  `variant`, `design_system`, `share_text`, `share_url`). Repointing would render `undefined`
  for every field. What is missing is the view-model mapping, not the data. This matters
  because the share card is the GTM "content loop" (VISION.md Step 2).
- `/leaderboard?sport=…` appears in raw grep output as a miss but is a false positive — it
  resolves and returns 200.

**Recommended order:** share-card view-model (small, unblocks GTM) → wellness → nutrition.
Invite/join should be deleted rather than built unless the coach-athlete binding is designed
first — see §2.3.

## 5. What is genuinely built (verified by reading the implementations)

Worth stating plainly, because the gaps above are real but the core is not vapour:

- `services/pose_analyzer.py` (932 lines) — real MediaPipe landmark maths, joint angles,
  quaternion torsion, dimensionless jerk, per-sport phase classification.
- `services/rppg_processor.py` (319 lines) — real CHROM algorithm, Butterworth bandpass,
  FFT-based BPM, RMSSD HRV from detected peaks.
- `pipeline/model_trainer.py` / `generate_dataset.py` — real Keras MLP with sklearn fallback.
- `ai_coach.py` — real Anthropic integration with circuit breaker + deterministic fallback.
- Backend: **117 passing tests**, 146 athletes / 547 sessions seeded, JWT auth verified
  end-to-end, injury-risk / weak-joints / streak endpoints call real compute functions.
- Frontend `server.js` — real proxy with WebSocket passthrough.
- Android `TrainScreen.js` — real `expo-camera` interval capture posting to the backend.

The pattern across all three repos is not "nothing is built" — it is **built but not wired
up**: on-device inference, invite links, billing, and the LLM key are each one connection
short of working.

## 6. Running the stack

```bash
# Backend — needs Python 3.12 (3.9 and 3.14 both fail to build deps)
cd personal-health-backend
/opt/homebrew/bin/python3.12 -m venv venv
source venv/bin/activate
brew install openblas
export PKG_CONFIG_PATH="/opt/homebrew/opt/openblas/lib/pkgconfig"   # scipy needs this
pip install -r requirements.txt
python3 api_server.py            # :8082

# Frontend
cd personal-health-frontend && npm install && node server.js   # :8083

# Android
cd personal-health-android && npx expo start
```

Note the cold Metro bundle took ~16 minutes on this machine.
